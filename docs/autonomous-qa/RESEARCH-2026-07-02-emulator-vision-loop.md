## 1. Containerized Android emulators with KVM under rootless podman

Baseline facts about the host target: Cuttlefish and the SDK emulator both require the host to expose KVM; Cuttlefish additionally needs the `vhost_vsock` and `vhost_net` kernel modules for guest I/O and networking ([source.android.com/docs/devices/cuttlefish/get-started](https://source.android.com/docs/devices/cuttlefish/get-started)). The standard container passthrough for the SDK emulator is `docker run --device /dev/kvm ...` ([github.com/google/android-emulator-container-scripts](https://github.com/google/android-emulator-container-scripts)).

**Rootless podman `/dev/kvm` caveat (verified):** rootless podman can silently fail to mount `/dev/kvm` when it is accessed through group membership; the documented workaround is to bind-mount the node with `-v /dev/kvm` instead of `--device /dev/kvm` ([containers/podman#16701](https://github.com/containers/podman/issues/16701)), corroborated by the Red Hat rootless-KVM/QEMU guidance ([developers.redhat.com/articles/2024/12/18/rootless-virtual-machines-kvm-and-qemu](https://developers.redhat.com/articles/2024/12/18/rootless-virtual-machines-kvm-and-qemu)). ACTION for Lava's Containers submodule: the `containerized.go` path that hard-requires `--device /dev/kvm` should carry a rootless-podman fallback to `-v /dev/kvm:/dev/kvm` plus a group-add for the `kvm` gid.

**Headless GPU (verified):** the SDK emulator's headless-safe configuration is `-no-window -gpu swiftshader_indirect` (SwiftShader = software GL, no host GPU dependency); `-no-accel -gpu swiftshader` is the fully-software fallback when KVM is unavailable ([codersera.com/blog/android-emulator-docker-without-kvm](https://codersera.com/blog/android-emulator-docker-without-kvm/)). Host-GPU passthrough into a container is not reliable across drivers; `swiftshader_indirect` is the reproducible choice for a gate. Keep CPU acceleration (KVM) and GPU rendering (SwiftShader) as separate concerns — KVM accelerates the guest CPU, SwiftShader handles GL without the host GPU.

**adb-over-TCP wiring (verified):** the container publishes 5555 (adb) and (for the Google scripts) 8554/8555 (gRPC); the host connects with `adb connect localhost:5555` ([github.com/google/android-emulator-container-scripts](https://github.com/google/android-emulator-container-scripts)). Google's images also expose a gRPC service to talk to the running emulator inside the container.

**Snapshot pitfall (matches Lava §6.I clause 6):** cold-boot is mandatory for gate runs; snapshot reuse is a known false-green source. This is an operational discipline, not an image feature — Lava already encodes it constitutionally.

## 2. Real-time full video recording that survives restarts and long (>3 min) sessions

**Root cause of the 3-minute limit (verified):** Android's `adb shell screenrecord` caps at 180s via a hardcoded constant `static const uint32_t kMaxTimeLimitSec = 180;` in the AOSP `screenrecord` binary ([maestro.dev/fixing-androids-3-minute-screen-recording-limitation](https://maestro.dev/fixing-androids-3-minute-screen-recording-limitation-4839abc74aee)). Two production-grade escapes:

1. **Binary rewrite (Maestro's approach, verified):** locate the little-endian `b4000000` (=180) in the compiled `screenrecord`, overwrite with a larger limit (e.g. 3600) using Radare2 (`wx`), and push the patched binary onto the device pool. Produces one uninterrupted file, no stitch seams, works across Android versions ([maestro.dev](https://maestro.dev/fixing-androids-3-minute-screen-recording-limitation-4839abc74aee)).
2. **scrcpy (verified, recommended for Lava):** `scrcpy` has no 3-minute cap and records to `.mp4`/`.mkv` via `--record-format` ([manpages.debian.org/testing/scrcpy/scrcpy.1.en.html](https://manpages.debian.org/testing/scrcpy/scrcpy.1.en.html)). It reads the device H.264/H.265 stream over ADB and muxes host-side, so recording is decoupled from the app process and survives app restarts within one session. scrcpy's own author notes it does not suffer the screenrecord time limit ([github.com/Genymobile/scrcpy/issues/1315](https://github.com/Genymobile/scrcpy/issues/1315)). Repo: https://github.com/Genymobile/scrcpy (Apache-2.0). scrcpy can record headless (no mirror window) — suitable for a container.

**Chunk-and-stitch alternative (verified tradeoff):** looping `screenrecord` to emit successive mp4 files and stitching with ffmpeg introduces a skip at each seam ([medium.com/@leland_40592/...](https://medium.com/@leland_40592/fixing-androids-3-minute-screen-recording-limitation-4839abc74aee)). Prefer scrcpy or the binary rewrite over this for gate evidence.

**Recording backends compared:**
- `adb screenrecord`: on-device, 180s cap, H.264, dies when the app/session resets. Necessary-but-limited.
- `scrcpy`: host-side capture over ADB, no cap, `.mp4`/`.mkv`, headless-capable, Apache-2.0. Best default.
- `ffmpeg x11grab`: captures a host X display — only relevant if the emulator renders to a host X server (noVNC/Xvfb path in `budtmo/docker-android`); couples the recording to the display server rather than the device.
- Emulator gRPC/console recording: Google's container scripts expose a gRPC service to the running emulator ([github.com/google/android-emulator-container-scripts](https://github.com/google/android-emulator-container-scripts)); the emulator also supports console-driven recording. Exact long-session behavior UNVERIFIED.
- `hansalemaos/adbnativeblitz`: wraps `screenrecord` with reduced per-frame subprocess overhead for faster continuous capture, MIT-ish (verify) ([github.com/hansalemaos/adbnativeblitz](https://github.com/hansalemaos/adbnativeblitz)). Niche.

**Tamper-evident chunking + hashing (verified primitives):** FFmpeg's `segment` muxer splits a stream into sequential files ([ffmpeg.org/ffmpeg-formats.html](https://ffmpeg.org/ffmpeg-formats.html)); FFmpeg's `hash` and `framehash` muxers compute cryptographic digests (MD5/SHA-256/etc.) over stream/frame data ([manpages.debian.org/stretch/ffmpeg/ffmpeg-formats.1.en.html](https://manpages.debian.org/stretch/ffmpeg/ffmpeg-formats.1.en.html)). Recommended Lava recipe (matches §11.4.128 raw-layout + curated-evidence discipline): record with scrcpy → segment into N-second chunks with the `segment` muxer → `sha256sum` each chunk → write a manifest where `chunk[i].prev_hash = sha256(chunk[i-1])` (a hash chain), so any single-chunk tampering breaks the chain. FFmpeg has no built-in chain-of-custody chaining; the chain is a thin shell wrapper the Containers submodule owns. UNVERIFIED: any single OSS tool that does the full record+segment+chain in one step (build it as Lava glue).

## 3. AI vision-analysis of test recordings to verify user-visible outcomes

Two families exist: (a) pixel/perceptual diff tools (BackstopJS, Argos, Aye Spy, Playwright visual comparisons) that catch regressions vs a golden baseline, and (b) VLM-as-oracle tools that answer natural-language assertions ("search results rendered", "download link visible") from a screenshot/frame — the latter matches Lava's §6.AB "rendering correctness not just presence" requirement and needs no golden baseline.

**Perceptual/diff baseline (complementary regression signal):** BackstopJS, Argos, Aye Spy are OSS ([percy.io/blog/open-source-visual-regression-testing-tools](https://percy.io/blog/open-source-visual-regression-testing-tools), [browserstack.com/guide/visual-regression-testing-open-source](https://www.browserstack.com/guide/visual-regression-testing-open-source)). They are web-oriented; for Android use them on captured screenshots. The 2026 industry trend is "Vision AI catches what pixel-diff misses" (semantic noise filtering, ignoring dynamic banners/animations) ([dev.to/drizzdev/mobile-visual-regression-testing-in-2026-...](https://dev.to/drizzdev/mobile-visual-regression-testing-in-2026-why-vision-ai-catches-what-script-based-tools-miss-2bfm)).

**Frame-sampling + assertion loop (how teams structure it):** the standard structure is: (1) record with scrcpy; (2) sample keyframes at scene changes or fixed cadence (ffmpeg `select='gt(scene,0.3)'` or `fps=1`); (3) feed each sampled frame + a natural-language assertion to the VLM; (4) require a structured JSON verdict (`{pass: bool, evidence: "...", confidence}`); (5) treat the VLM verdict as a secondary CI signal that must agree with the Espresso/Compose assertion — divergence flags a bluff. This mirrors Lava's §6.AK "gate-coverage must intersect cycle-claims": the VLM verifies the same user-visible outcome the Challenge claims. UNVERIFIED: a single turnkey OSS "video→assertion CI gate" for Android; assemble from Midscene + ffmpeg sampling.

## 5. Game-changing / novel approaches worth flagging

- **Google Cuttlefish (`cvd`) — self-hostable "AWS Device Farm equivalent" (verified).** Configurable virtual Android device, runs locally (x86 + ARM64) or in cloud; official on-prem path is the **Cuttlefish Docker image + Cloud Orchestrator web service**; couples with Kubernetes for elastic fleets ([source.android.com/docs/devices/cuttlefish/on-premises](https://source.android.com/docs/devices/cuttlefish/on-premises), [realz.medium.com/running-android-on-kubernetes](https://realz.medium.com/running-android-on-kubernetes-be73b940833f)). Repos: https://github.com/google/android-cuttlefish (Apache-2.0), community https://github.com/thatoddmailbox/cuttlefish-docker. Needs KVM + `vhost_vsock`/`vhost_net`. This is the highest-fidelity self-hosted device-farm primitive and a strong candidate to back Lava's §6.AE matrix at scale (multiple API levels as k8s pods). It is still KVM-in-a-container (not fully isolated) ([source.android.com/docs/devices/cuttlefish/on-premises](https://source.android.com/docs/devices/cuttlefish/on-premises)).
- **redroid microVM-free path (verified).** Real Android userspace on the host kernel (binder/ashmem), no QEMU, no `/dev/kvm` — the fastest headless option on runners lacking nested virt ([github.com/remote-android/redroid-doc](https://github.com/remote-android/redroid-doc)). Novel for cost, but device-parity with the SDK AVD is UNVERIFIED for gate fidelity.
- **DeviceFarmer / STF (verified, caveated).** OSS continuation of OpenSTF: browser control of real device fleets, REST API for CI, booking/partitioning; v3.7.7 (2025-07-23); **volunteer-maintained, slow progress** ([github.com/DeviceFarmer/stf](https://github.com/DeviceFarmer/stf), [medium.com/@jerimiahham/building-device-farms-with-stf](https://medium.com/@jerimiahham/building-device-farms-with-stf-a-9-year-journey-and-gift-to-the-community-1050a530bd58)). Fits Lava if physical devices are added later; heavier than needed for emulator-only gates.
- **Genymotion Device Image / PaaS (verified, non-OSS).** Android AMIs on AWS/GCP/Alibaba/Azure, per-minute-per-device pricing, plus on-prem; ARM64 images up to Android 15 ([genymotion.com/product-device-image](https://www.genymotion.com/product-device-image/), [aws.amazon.com/marketplace ... Genymotion PaaS Android 15](https://aws.amazon.com/marketplace/pp/prodview-wwjcsmbxgbboy)). Not OSS and cloud-cost-bearing — conflicts with Lava's Local-Only CI/CD and §6.W posture; flag as a fallback only.
- **Maestro for Compose (verified, Apache-2.0).** Black-box UI automation that reads Compose semantics automatically and prioritizes text/semantics over `testTag`; `testTagsAsResourceId = true` exposes tags; `maestro hierarchy` dumps targets ([docs.maestro.dev/platform-support/android-jetpack-compose](https://docs.maestro.dev/platform-support/android-jetpack-compose)). Novel vs Espresso: no instrumentation coupling, YAML flows, resilient to refactors — a lighter complement (not replacement) to Lava's Compose Challenge Tests, and the source of the screenrecord binary-rewrite technique in §2.
- **Midscene + self-hosted VLM as an appium alternative (verified).** Natural-language, selector-free Android automation over ADB with local UI-TARS/Qwen — no Appium server, no brittle locators ([github.com/web-infra-dev/midscene](https://github.com/web-infra-dev/midscene)). This is the "vision agent drives the app AND verifies it" convergence of §3 and §5.
