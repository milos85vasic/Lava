# Onboarding flow audit — 2026-06-13

Operator directive: "create full automation tests for all onboarding scenarios, fix all
issues and INCONSISTENCIES." Scope: `feature/onboarding/`.

Flow: `Welcome → ApiSelection → Providers → Configure → Summary`. Reviewed the ViewModel,
every step Composable, every action handler, and all existing tests against the §6.AB
completeness checklist (state-machine completeness, gating logic, rendering correctness).

## Method

Every `OnboardingAction` handler in `OnboardingViewModel.kt` was traced. Every step
transition (forward + back) was walked. The existing JVM test suite
(`OnboardingViewModelTest`, `OnboardingViewModelDynamicProvidersTest`, `OnDeviceApiFlowTest`,
`CloudApiDefaultsTest`, `AuthTypeDisplayTest`, `OnboardingInsetRegressionTest`) was indexed
to find scenarios with no falsifiable automation test.

## Findings

### F1 — INCONSISTENCY (fixed): back-from-ApiSelection→Welcome reset is incomplete
`OnboardingViewModel.onBackStep()` ApiSelection branch resets `discoveredApis`, `selectedApi`,
`apiConnectivity`, `apiDiscoveryRunning` — but leaves `cloudAddressInput`, `cloudAddressError`,
and `providerCatalogNotice` stale. `startApiDiscovery()` (the forward re-entry) resets the
cloud fields but NOT `providerCatalogNotice`. The back-cleanup is therefore asymmetric with
the forward-entry cleanup, and a stale `providerCatalogNotice` / `cloudAddressError` can
survive a Welcome round-trip.
- File: `feature/onboarding/src/main/kotlin/lava/onboarding/OnboardingViewModel.kt`
  `onBackStep()` ApiSelection branch (lines ~382-393) + `startApiDiscovery()` (~201-216).
- Why wrong: §6.AB state-machine completeness — a back transition must leave the prior
  screen in a clean state; a stale user-visible error banner / fallback notice is a
  rendering-correctness defect.
- Fix: clear `cloudAddressInput`, `cloudAddressError`, `providerCatalogNotice` on
  back-to-Welcome AND clear `providerCatalogNotice` on `startApiDiscovery()` re-entry.

### Coverage gaps (no falsifiable JVM ViewModel test) — addressed by new tests
All existing `OnboardingViewModelTest` cases run with `apiSelectionEnabled=false`, so the
ApiSelection-enabled state machine was effectively untested at the ViewModel layer. The
discovered-list probe-success/failure/retry paths and the credential success/failure paths
had no ViewModel test.

- G1 `apiSelectionEnabled=true`: Welcome→ApiSelection enters ApiSelection (not Providers).
- G2 ApiSelection discovered-list SelectApi **success** → advances to Providers.
- G3 ApiSelection SelectApi probe **failure** → `apiConnectivity = Failure`, NO advance.
- G4 ApiSelection `RetryApiProbe` after failure → success advances.
- G5 Back from Providers when `apiSelectionEnabled=true` returns to **ApiSelection**.
- G6 Back from ApiSelection→Welcome clears discovery + cloud + notice state (F1 regression).
- G7 `TestAndContinue` FORM_LOGIN credential **success** persists credentials + advances.
- G8 `TestAndContinue` FORM_LOGIN credential **failure** (`AuthState != Authenticated`) →
  `error = "Invalid credentials"`, NO advance, `connectionTestRunning = false`.
- G9 `TestAndContinue` **exception** path → `config.error` carries the throwable message.
- G10 `onFinish` with a FORM_LOGIN credentialed provider signals authorized with the
  username (not "Anonymous").

### F2 — DOCUMENTED LIMITATION (not fixed — out of scope / would be gold-plating)
`ConfigureStep` renders Username+Password fields for every non-anonymous provider, including
`AuthType.API_KEY`, `CAPTCHA_LOGIN`, `OAUTH`. The onboarding ViewModel's credential path only
handles `LoginRequest(username, password)` — there is no API-key persistence wired into
onboarding at all. Introducing a key-field UI without the matching VM persistence would be a
half-wired bluff feature. Recorded as a limitation; the per-provider key entry happens
post-onboarding via Provider Config. No production change made.

### Non-findings (traced, confirmed correct — NOT bugs)
- `onNextStep` Providers→Configure correctly refuses when zero providers selected.
- `onFinish` gate correctly refuses to emit `Finish` unless ≥1 provider is `configured && tested`.
- Back-from-Welcome correctly posts `ExitApp` (NOT `Finish`) — the historical gate-bypass.
- `loadProviders` correctly filters `verified && apiSupported && trackerId !in syntheticIds`.
- `TestAndContinue` null-login (no-auth tracker) correctly treated as success (Finding #7).
- Cloud add: valid→probe→advance; malformed→error→no-advance (already tested).
- On-device API return persists the keyed endpoint + advances (already tested).
