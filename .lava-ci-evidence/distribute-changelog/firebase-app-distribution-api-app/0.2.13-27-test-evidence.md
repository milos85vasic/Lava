## Build-corruption incident found + fixed during this cycle's gate (honest, per §6.J)

The first gate attempt for this version FAILED with a real, reproducible
Android-runtime error: `NoClassDefFoundError: dagger/hilt/internal/
GeneratedComponentManager`, caused by `Failure to verify dex file ...:
Bad checksum (a3acee6c, expected 6badee62)`. Root-caused (not guessed):
the on-disk `api-app/build/outputs/apk/debug/api-app-debug.apk` was
genuinely corrupted (`unzip -t` reported "At least one error was
detected"), produced by an earlier build where this gate's own Gradle
invocation ran CONCURRENTLY with a separate `:app:assembleDebug
:app:assembleRelease` Gradle invocation against the same monorepo,
racing on shared `core:*` module outputs both apps depend on. Gradle's
own UP-TO-DATE check then silently reused the corrupted artifact across
a second attempt (since neither the build script nor the file's mtime
had changed). Fixed by deleting `api-app/build/outputs/apk` +
`api-app/build/intermediates` entirely and rebuilding sequentially (no
concurrent Gradle invocation against the same repo), then verifying
`unzip -t` reports no errors on both the app and androidTest APKs before
re-running the gate. This is a build-hygiene lesson (never run two
Gradle invocations concurrently against the same monorepo — even against
different modules, they can race on shared dependency outputs), not a
product defect; recorded here rather than silently retried without
explanation.

A separate, unrelated JVM instability was also observed and resolved
during this cycle: `:api-app:assembleRelease` (R8 minification + a
189MB-uncompressed native-`.so`-bundling APK) crashed the build JVM with
an identical `SIGSEGV` in a G1GC worker thread on 3 consecutive attempts
at the default `-Xmx4096m` heap, host memory otherwise healthy
(10GB+ free each time). A 4th attempt at `-Xmx6144m` (`-Dorg.gradle.
jvmargs="-Xmx6144m"`) completed cleanly (`BUILD SUCCESSFUL in 7m 45s`),
and the resulting APK verified intact via `unzip -t`. Recorded as a
build-environment finding, not a code defect — api-app's release build
appears to need a larger heap than the client's does.
