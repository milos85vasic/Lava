## Scope — LVA-098 (P0: no tracker could log in, search failed for every provider)

Root cause: `app/build.gradle.kts`'s `afterEvaluate { android.sourceSets["debug"]
.kotlin.srcDir(...) }` pattern that wires the `LavaAuthCodegen`-generated
`lava/auth/LavaAuthGenerated.kt` source directory into the debug/release
Kotlin compilation ran too late on this project's AGP 8.6.1 + Kotlin 2.1.0
combination for `compileDebugKotlin`/`compileReleaseKotlin` to pick it up.
The codegen task genuinely ran and wrote the file to disk every build, but
it was **never compiled into the APK** — confirmed via `dexdump -l xml`
across all 20 `classesN.dex` files in the built debug APK: zero
`class_def_item` matches for `lava.auth.LavaAuthGenerated` (the class name
only appeared as a string-literal constant, the argument to
`AuthInterceptorModule.tryLoadGenerated()`'s `Class.forName(...)` call).

Net effect on every real device, every build, since this wiring was
introduced: `Class.forName("lava.auth.LavaAuthGenerated")` threw
`ClassNotFoundException`, `AuthInterceptorModule` silently fell back to the
empty `StubLavaAuthBlobProvider`, and **every authenticated request left the
device with no `Lava-Auth` header at all** — regardless of which tracker
provider, regardless of credentials, regardless of any server-side identity
configuration. This is the root cause of the reported "not a single tracker
can log in through onboarding, and the ones which don't require login can't
search either" — every one of those flows routes through lava-api-go's
`AuthMiddleware`, which correctly and unavoidably 401s a request carrying no
header at all.

Fix: moved the `srcDir` registration for both the `debug` and `release`
source sets to an eager, top-level statement in `app/build.gradle.kts`
(outside `afterEvaluate`) — proved via a throwaway task dumping
`compileDebugKotlin.sources` and grepping for `lava-auth`: 0 matches with
the old wrapped registration, 1 match with the eager registration. An
AGP Variant-API alternative (`androidComponents.onVariants { variant.sources
.kotlin.addStaticSourceDirectory(...) }`) was tried first and also fired
correctly at configuration time but produced 0 matches — this project's
KGP version does not read from that AGP Sources model for this integration
path, so the fix is specifically the eager legacy-DSL call, not the API
choice.

Also landed this cycle (§6.AC, permanent, not temp diagnostics): local
logcat-visible logging in `AuthInterceptorModule.tryLoadGenerated()` (client)
and in `lava-api-go`'s `AuthMiddleware`/`router.Build`'s global request
logger (server) — closing a real gap where a 401 was previously
indistinguishable from "request never arrived" from `podman logs` alone,
which is what made this investigation far harder than it needed to be.
