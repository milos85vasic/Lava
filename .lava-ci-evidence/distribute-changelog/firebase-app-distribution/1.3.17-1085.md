# Lava-Android-1.3.17-1085 — LVA-098, P0 auth-blob build-wiring fix

**Previous published:** Lava-Android-1.3.17-1084.

- **Root cause:** `app/build.gradle.kts` wired the build-time-generated `lava.auth.LavaAuthGenerated` Kotlin source into the debug/release compilation via `afterEvaluate { android.sourceSets["debug"].kotlin.srcDir(...) }`, which ran too late on this project's AGP 8.6.1 + Kotlin 2.1.0 combination for the Kotlin compile task to see it. The class was written to disk every build but never compiled into the APK's dex (confirmed via `dexdump` — 0 class definitions across all 20 dex files).
- **Effect:** `AuthInterceptorModule` silently fell back to an empty auth-blob stub on every real device, so no authenticated request ever carried a `Lava-Auth` header — the root cause of "no tracker can log in, search fails for every provider."
- **Fix:** moved the source-directory registration to an eager, non-`afterEvaluate` top-level statement. Verified via a throwaway Gradle diagnostic task (`compileDebugKotlin.sources`: 0 lava-auth matches before, 1 after).
- **Device-verified, not just source-patched:** real non-instrumented device launch now logs `LavaAuthGenerated FOUND`; `Challenge70AutonomousQaProviderMatrixTest` PASSED end-to-end against the real backend; server-side logs independently confirm `hdr_present=true` + matched client identity + HTTP 200 on search/topic/download.
- **Also landed:** permanent §6.AC local (logcat/server-log) telemetry for auth-blob resolution and request/auth outcomes, closing the silence that made this bug hard to diagnose.
