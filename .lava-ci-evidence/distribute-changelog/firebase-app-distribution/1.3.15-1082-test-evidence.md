## §6.AA Stage 2 — release authorization

**Operator confirmed in writing (in-session, 2026-08-12):** the Firebase-distributed debug variant (1.3.15-1082) was installed and tested on a real device and works correctly. Recorded here per §6.AA clause 2 before running `firebase-distribute.sh --release-only --app client`.

**Agent-side release-artifact device verification (in-session, 2026-08-12):** the operator additionally directed the agent to independently verify the actual RELEASE artifact on-device, not rely on the debug-build evidence alone (§6.Z.5's "R8/minification surprise class" — a release-only bug is exactly the 1.2.19 forensic anchor this project's §6.AA exists to prevent). This surfaced that the Containers submodule's `RunCanary` tool — the only mechanism that can verify a release-signed APK at all, since instrumented tests cannot run against one (signature mismatch) and a debuggable release build has R8 entirely disabled — had never been runnable on Linux (host-direct only, violating this project's own §6.AH). Closed that gap for real: added a `RunADBCommand` primitive to the `Emulator` interface + containerized-runner support to `emulator-canary` (Containers commit `7fa49f7`, full package test suite PASS). The FIRST real end-to-end run against this exact release APK then surfaced a SECOND real bug: the canary's resumed-activity detection used a stale dumpsys field name (`mResumedActivity`) that Android 14 (API 34) no longer emits — a genuine false-negative in the verification tool, confirmed by inspecting the actual captured dumpsys output showing `state=RESUMED` for the real launched activity. Fixed with a regression test built from the real captured output (Containers commit `0381fe0`). Re-run after both fixes: **`activity_resumed: true, fatal_detected: false, passed: true`** — genuine PASS on the actual, non-debuggable, R8-minified release APK. Evidence: `.lava-ci-evidence/release-canary-containerized-1.3.15-1082-fixed/canary-attestation.json`. The intermediate failed/diagnostic runs (`-diag`, `-longtimeout`, `-retry`, and the initial run) are kept for the honest record of the discovery process rather than only keeping the final pass.

**Auth-identity rebuild note:** the §6.P distribute gate required rotating `LAVA_AUTH_OBFUSCATION_PEPPER` (reuse-across-releases check) and registering a new `LAVA_AUTH_CURRENT_CLIENT_NAME`/`LAVA_AUTH_ACTIVE_CLIENTS` entry (`android-1.3.15-1082`) in `.env` — both gitignored, non-tracked, so neither changes the commit SHA above. `buildSrc/LavaAuthCodegen.kt` bakes these into the APK at build time, so the artifact was rebuilt AFTER this `.env` update (the artifact `aapt`-verified below is the post-rotation rebuild). The 7 Challenges below ran against the PRE-rotation build (same source SHA, prior `.env` auth identity) — none of them exercise the real production HMAC client-allowlist handshake (they drive UI/search/dialog flows against `MockWebServer`/`ApiBaseUrlHolder`, not the live auth path), so this is not a coverage gap for what these Challenges actually claim to verify. Flagged here for full honesty per §6.J rather than left implicit.
