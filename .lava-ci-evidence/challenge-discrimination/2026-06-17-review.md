# §6.AB Challenge-Discrimination Review — 2026-06-17

READ-ONLY static review of every `app/src/androidTest/kotlin/lava/app/challenges/Challenge*Test.kt`
(45 files). Each verdict is based on the **actual `@Test` body assertions** read from source, not the
KDoc claims. Where a KDoc describes a stronger test than the code implements, that gap is the finding.

§6.AB requires every Challenge to FAIL when the user-visible feature breaks in a plausible
NON-CRASHING way (white-on-white icon, gate firing on wrong condition, wrong nav destination, dead-end
side effect). A test whose chief assertion is only "node exists" / "class on classpath" / "no crash" /
a trivially-true condition is WEAK by that standard.

## Cross-cutting notes

- The C30–C35 + C37TopicAddComment cluster all share the same root cause: `internal`-visibility feature
  ViewModels are not referenceable from the `:app` androidTest source set, so the authors fell back to
  `Class.forName`/`::class.java` name checks as a §6.AE coverage-scanner satisfier. They satisfy
  `check-challenge-coverage.sh` (the feature is "covered") but NOT §6.AB discrimination. The fix pattern
  already exists in the STRONG siblings (C07/C08/C26/C30Cloud/C37OnDevice): render the feature's public
  composable directly via `createComposeRule().setContent { ... }` and assert on rendered nodes +
  capture callbacks — no `internal` access needed because the screen-level composables are public.
- C13 and C15 are intentionally boot/cold-start canaries; "reached UI without crash" IS their
  user-visible contract, so they are correctly STRONG for their class — they are NOT a substitute for
  behavioral coverage of the features they boot past.
- Several STRONG tests are gated (`assumeTrue`) on credentials / verified descriptors / configured gate
  hosts (C02/C09/C10/C11/C38/C39/C40). Their gating is honest (skip ≠ pass), but on a real gate run the
  operator must confirm the gates are satisfied or those rows are skips, not passes.

### Still WEAK (8): blocked on a PRODUCTION visibility change — NOT a test-only fix

Verified by reading the production composable signatures. Each feature's
deterministic state-rendering composable (the one that draws content for a given
state, the surface C30 renders for `ApiSelectionStep`) is `private` or `internal`,
so the `:app` androidTest source set CANNOT reference it to render it standalone —
which is exactly why the authors fell back to `Class.forName` / function-ref checks.
The STRONG-renderable siblings (C30 Cloud, C26, SummaryStep) work ONLY because their
`feature/onboarding` step composables were deliberately published `public`.

Closing these 8 genuinely (render the public stateless composable + assert rendered
nodes/callbacks, the review's "Add:" pattern) requires the main coordinated build to
FIRST widen the per-feature state-renderer from `private`/`internal` to `public`
(a product-surface change, owned by the feature module), THEN the androidTest can
render it like C30. Signatures confirmed:
