## The max_map_count question (the documented blocker on Linux hosts)

SonarQube's embedded Elasticsearch needs `vm.max_map_count >= 262144`. On THIS
host the value inside the podman `applehv` VM is already:

```
/proc/sys/vm/max_map_count = 1048576
```

— well above the 262144 minimum, so Elasticsearch started cleanly with NO root
sysctl change and NO `sudo`. The compose file deliberately sets neither a
`sysctls:` block nor `privileged: true`.

On a host where the runtime VM / kernel reports a value below 262144, the
`sonarqube` container's ES sub-process would refuse to start and the container
would stay unhealthy. Raising it there is an OPERATOR / GATE-HOST action
performed OUTSIDE this project's scripts (§6.U) — documented per-OS in
`docs/security/2026-06-04-sonarqube-snyk-setup.md`.

## Scanner step — NOT run in this bring-up (honest)

The `scan` subcommand requires `SONAR_TOKEN`, which is generated in the Sonar UI
after the first admin login (a one-time interactive step). Server-up is proven
above; the scan is gated on the token per `scripts/sonar-scan.sh scan` and is
left as the operator's next action. No scan results are fabricated.
