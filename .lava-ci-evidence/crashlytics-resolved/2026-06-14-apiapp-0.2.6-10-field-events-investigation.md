# Investigation — api-app 0.2.6 (10) field events surfacing under the CLIENT release Firebase app

- **Date:** 2026-06-14
- **Trigger:** Overnight field-monitor heartbeat #5 — `topVersions` on the CLIENT release Firebase app (`1:815513478335:android:456475e2ef4039d8cfd20a`) showed `0.2.6 (10)` with 4 events at the TOP, above the real client versions (1.3.5/1.3.4). `0.2.6 (10)` is the **api-app** version, not a client version. Heartbeats #1–#4 did not show it.
- **Classification:** project-specific (Lava field-regression forensic).
- **Status:** ANALYSIS ONLY — no code changed. Verdict + recommendation below.

## Verdict

**(C) BOTH** — real api-app FATAL crashes AND a telemetry-attribution misconfiguration.

1. The 4 events are **REAL FATAL crashes** emitted by the api-app (`digital.vasic.lava.api`, artifact `api-app`, build_type `release`, version 0.2.6 / code 10) running on a real device.
2. They are **misattributed** to the CLIENT release Firebase app id because `api-app/google-services.json` carries the CLIENT's `mobilesdk_app_id` values (with api-app package names pasted over them). The api-app's own Firebase apps receive **zero** Crashlytics data.

## Root cause (file:line)

### Defect 1 — telemetry attribution misconfig (google-services.json mismatch)

`api-app/google-services.json` maps the api-app package names onto the **CLIENT's** Firebase app ids:

- `api-app/google-services.json:10-12` → `mobilesdk_app_id: 1:815513478335:android:456475e2ef4039d8cfd20a` with `package_name: digital.vasic.lava.api`.
  - But `app/google-services.json:10-12` maps that SAME id `456475e2…` to `package_name: digital.vasic.lava.client`. (Per `firebase_list_apps`, `456475e2…` = "Lava Android" = client release.)
- `api-app/google-services.json:29-31` → `mobilesdk_app_id: 1:815513478335:android:54ca2ca31e6c4f42cfd20a` with `package_name: digital.vasic.lava.api.dev`.
  - But per `firebase_list_apps`, `54ca2ca3…` = "Lava Android (Debug)" = `digital.vasic.lava.client.dev` (client debug).

The two REAL api-app Firebase apps are **absent** from `api-app/google-services.json`:
- `.api` release = `1:815513478335:android:d57b960e955645f6cfd20a`
- `.api.dev` debug = `1:815513478335:android:2932451e07ca80a7cfd20a`

Because the Crashlytics SDK keys reporting on the `mobilesdk_app_id` in the bundled `google-services.json`, the api-app reports under the client release app id. This is a §6.AC telemetry-honesty issue: the api-app correctly records, but to the wrong Firebase app — and it pollutes the client's `topVersions`, hiding real client regressions behind a non-client version.

`api-app/build.gradle.kts:71` confirms `applicationId = "digital.vasic.lava.api"` (`:150` adds `.dev` suffix for debug), so the correct app ids are `d57b960e…` / `2932451e…`, not the ones pasted into the JSON.

### Defect 2 — real `dataSync` foreground-service time-limit crashes

`api-app/src/main/kotlin/lava/api/app/service/ApiEngineService.kt:113`:
```kotlin
override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
    startForeground(NOTIFICATION_ID, buildNotification(getString(R.string.api_notification_title)))
    ...
```
The service runs as a `dataSync`-typed foreground service. On Android 14+ (these events are Android 16), `dataSync` has a cumulative ~6h/24h runtime budget. Once exhausted:
- a subsequent `startForeground` throws `ForegroundServiceStartNotAllowedException` → **issue 9ba8502e…** (crash at line 113), and
- the OS forcibly stops the overrunning service → `ForegroundServiceDidNotStopInTimeException` → **issue b9baeaede…**.

These are genuine api-app lifecycle bugs (the api engine is a long-lived LAN service, which is structurally at odds with the `dataSync` time budget), NOT artifacts of the misattribution. They reproduce on the api-app regardless of which Firebase app the telemetry lands on.

## Recommendation

### Severity
- Defect 1 (attribution): **medium** — no user-facing crash from the misconfig itself, but it corrupts the client's crash dashboard (false `topVersions` row, real client regressions masked) and leaves the api-app's real Firebase apps blind. A §6.AC honesty issue.
- Defect 2 (`dataSync` crashes): **real FATAL on the api-app** — but low field volume (4 events / 1 user / 1 device so far, fresh tonight) and BACKGROUND process state. It is a real blocker for the api-app's reliability, not a client blocker.

### Concrete fixes
1. **Defect 1 — fix `api-app/google-services.json`.** Replace the two client app ids with the api-app's real ones:
   - entry for `digital.vasic.lava.api` → `mobilesdk_app_id: 1:815513478335:android:d57b960e955645f6cfd20a`
   - entry for `digital.vasic.lava.api.dev` → `mobilesdk_app_id: 1:815513478335:android:2932451e07ca80a7cfd20a`
   Regenerate from the Firebase console (`.api` + `.api.dev` apps) rather than hand-editing, to also fix the `api_key`. After the fix, the next api-app build's crashes land on `d57b960e…`/`2932451e…` and stop polluting the client release dashboard.
2. **Defect 2 — `ApiEngineService` `dataSync` budget.** Options (for operator decision, not part of this analysis): switch the FGS type away from `dataSync` for a persistent LAN service (e.g. `connectedDevice`/`specialUse` with the manifest declaration + Play policy justification), or handle `ForegroundServiceStartNotAllowedException` / the timeout callback gracefully (stop + reschedule) instead of letting it crash at line 113.

### Timing — fix-now-safely vs wait-for-operator
- **Defect 1 (google-services.json): SAFE to fix now.** It is a config-only change to a gitignored-pattern file under `api-app/`; it cannot brick the client (the client's own `app/google-services.json` is correct and untouched). It is low-risk and stops the dashboard pollution. RECOMMEND fixing tonight, then re-gate (§6.Z cold-start canary on the api-app) before any redistribute — note the api-app must still be rebuilt + re-distributed for the fix to take effect on devices already running 0.2.6-10.
- **Defect 2 (`dataSync` lifecycle): WAIT for operator sign-off.** It is a foreground-service-type / Play-policy decision with real product trade-offs (LAN service longevity vs Android FGS budgets) and needs a design choice + §6.AE Challenge coverage. Not an overnight blind fix. Low field volume (1 user) means it is not an emergency.

### Net
No client-side regression: the 4 events are NOT a client crash. The client 1.3.5/1.3.4 rows (3+3 events) are the real client signal and were not analyzed here. The actionable overnight item is **Defect 1** (config fix, then rebuild + re-gate + re-distribute the api-app); **Defect 2** waits for operator sign-off.
