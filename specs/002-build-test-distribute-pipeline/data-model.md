# Phase 1 Data Model: Local Build-Test-Distribute Pipeline

All entities below are file-based records (JSON unless noted), per `research.md` R-008. None of this feature's entities are stored in `docs/workable_items.db` or any other SQLite store — they are pipeline-run artifacts under `.lava-ci-evidence/pipeline-runs/`, consistent with this project's existing evidence-directory conventions.

> **Reconciled against the implementations on 2026-08-21**, in the same pass and to the same standard as `contracts/cli-contract.md`. Every field, path and validation rule below was checked against the script that actually reads or writes it. **Where the code and this document disagreed, the code won and this document was corrected**, with the correction called out inline rather than quietly rewritten — a data model that describes fields nobody writes is a bluff about the shape of the system, and the next agent will act on it. Three classes of correction appear below: (a) entities that were designed and never built (Distribution Record); (b) fields that were designed and are not persisted (`current_phase`, the whole Infrastructure Service record); (c) **validation rules that turned out to be unenforceable as originally written** and had to be strengthened in the implementation (`raw_output_ref`'s exist-and-non-empty rule, and the Pipeline Run Report's own `rejected_by_anti_bluff` rule). Class (c) is the important one and is called out explicitly at each site.

## Pipeline Run

One directory per invocation: `.lava-ci-evidence/pipeline-runs/<run_id>/`.

| Field | Type | Notes |
|---|---|---|
| `run_id` | string | The directory name itself: `<UTC-timestamp>` (e.g. `2026-08-21T14-30-00Z`), per R-010 — unique per invocation, never reused. |
| `commit_sha` | string | The `master` HEAD commit at invocation time (FR-000 guarantees this is also a clean tree). |
| `started_at` / `completed_at` | ISO-8601 string | Wall-clock bounds; no derived duration ceiling per spec Clarification (no fixed time limit). |
| `current_phase` | enum | **CORRECTED 2026-08-21: designed, never built, and not persistable as specified.** This document used to describe `current_phase` as a tracked field with the enum `precondition, build, test, install_boot, live_verify, changelog_entry, distribute, docs_refresh, closure, complete, failed`. The identifier `current_phase` appears nowhere in `scripts/`, `tests/`, or any schema — only in this table. `contracts/pipeline-run-report.schema.json` sets `"additionalProperties": false` and does not list it, so writing it into `report.json` would make the report fail its own schema. What actually exists is the orchestrator's in-memory loop variable `phase_name` (`scripts/pipeline-build-test-distribute.sh`, the `for entry in "${PHASES[@]}"` loop), which is never written anywhere. The design intent — "tracked only for the duration of a single run, never read by a later run (FR-018)" — is satisfied more strongly by not persisting it at all. The two terminal values `complete`/`failed` were superseded by the report's own `outcome` field. |
| `outcome` | enum | `PASS` \| `FAIL` \| `BLOCKED`. `BLOCKED` is the value `init_run_report` writes the moment `report.json` is created; `finalize_run_report` only ever writes `PASS`/`FAIL` (see that function's own header and Check 4a-4e in `tests/pipeline/test_evidence_and_run_report.sh`, including the deliberate "empty phases[] → FAIL, never PASS" rule of Check 4c). **CORRECTED 2026-08-21 — the previous text got the precondition case exactly backwards.** It used to read: *"It does NOT mean 'precondition refusal': per quickstart.md Scenario 1, a precondition (phase-00) refusal happens strictly BEFORE `init_run_report` is ever called, so it produces no `report.json` at all — there is nothing to mark `BLOCKED`, by design ('a refused run must not fabricate a run report for a run that never started')."* The orchestrator does the opposite, deliberately: `init_run_report` is called **before** the phase loop runs at all, because a refusal to start is itself a run outcome and must be recorded. So an FR-000 refusal **does** create `.lava-ci-evidence/pipeline-runs/<run_id>/report.json`; the orchestrator appends a `precondition`/`FAIL` entry on phase-00's behalf, then runs `recompute_evidence_summary` + `finalize_run_report` on the way out, so a refused run finalizes to `outcome: "FAIL"` — never `BLOCKED`, and never a fabricated `PASS`. That ordering is also why `.gitignore` must ignore `.lava-ci-evidence/pipeline-runs/` (task T003): without it the pipeline dirties the tree it is about to test and can never satisfy FR-000, and the orchestrator carries a dedicated `DIAGNOSIS` branch for exactly that case. In practice `BLOCKED` therefore survives to rest **only when `finalize_run_report` never ran at all** — a `SIGKILL`, a host crash, or a failure inside finalize itself. `SIGINT`/`SIGTERM` do not qualify: the orchestrator traps both and closes the report, so an operator-cancelled run also finalizes to `FAIL`. |

**Validation rules**: `run_id` MUST be lexicographically sortable by creation time (UTC-timestamp format guarantees this, matching the existing `.lava-ci-evidence/verify-all/<timestamp>.json` convention). A Pipeline Run directory MUST NOT be read as input by any other Pipeline Run (R-010) — enforced by convention (no code path takes a `run_id` as input except the run currently writing to it) rather than a lock file, since concurrent runs are out of scope (FR-000 requires a clean `master` tree, and a running pipeline's own build/test activity would itself dirty the tree for any second invocation).

**CORRECTED 2026-08-21 — one half of this rule is now mechanical, not conventional.** `init_run_report` refuses (non-zero + stderr) when `report.json` already exists for the given `run_id`, so a second run can no longer silently overwrite an earlier run's report. The other half — never *reading* another run's directory as input — remains convention-enforced, and no code path violates it. One consequence worth stating because it is load-bearing for `quickstart.md` Scenario 5: `run_id` is `date -u +%Y-%m-%dT%H-%M-%SZ`, i.e. **one-second resolution**, so two invocations started inside the same second collide and the second one is refused by that same check rather than corrupting the first.

## Evidence Record

One JSON file per executed test: `.lava-ci-evidence/pipeline-runs/<run_id>/phase-<NN>/<category>/<test_id>.json`.

| Field | Type | Notes |
|---|---|---|
| `test_id` | string | Fully-qualified test name (e.g. `lava.login.LoginViewModelTest#validateUsername_clearsStaleServiceUnavailable`, or a bash suite's own test-function name). |
| `category` | enum | One of R-011's 8 mapped categories. |
| `command` | string | The exact command invoked (for independent re-run, per FR-003's "sufficient for independent re-verification"). |
| `result` | enum | `PASS` \| `FAIL` \| `SKIPPED`. `SKIPPED` covers a test that legitimately, honestly did not execute — either the test itself self-skips for a documented reason (e.g. a Go test's own `t.Skip("POSTGRES_TEST_URL not set")`) or an entire check is BLOCKED by a missing host precondition (e.g. Genymotion not installed). Forcing an honest skip into `FAIL` would be misleading (it is not a real defect); forcing it into `PASS` would be an outright bluff (fabricating a pass for something that never ran) — `SKIPPED` exists so neither workaround is necessary. |
| `assertion_summary` | string | The real, specific checked outcome (e.g. "expected 0 entries, got 0" — not "no crash"). For a `SKIPPED` record this MUST still be real and specific — e.g. quoting the actual skip reason — not a generic placeholder; see the Validation rules below. |
| `raw_output_ref` | string | **CORRECTED 2026-08-21 — the rule as originally written was literally unenforceable, and this is the most important correction in this document.** It used to say only: "Relative path to the captured stdout/stderr this record summarizes. MUST exist and be non-empty (R-009 rule c)". Two things were left unstated, and the gap between them was a real hole in the anti-bluff gate. (1) **Relative to what.** `write_evidence_record` re-expresses whatever path a caller hands it (absolute, or relative to the pipeline's working directory) as a path relative to **the record file's own directory**, `<phase_dir>/<category>/`, because that is the base `anti-bluff-validate.sh` resolves it against. Without that normalization a caller following the pipeline's ordinary convention would have produced a ref that resolved one level too deep and was reported missing. (2) **"Exists and is non-empty" does not exclude a directory.** An absent or empty `raw_output_ref` resolved to `"<record_dir>/"` — the record's own directory — and a directory inode satisfies both the exists test and the non-empty test, because it has a non-zero size. So a record that asserted nothing and pointed at nothing passed every rule below it vacuously and was stamped `"validated"`. The validator now requires the resolved path to be a **regular file** (`-f`, not `-e`) that is non-empty, and separately rejects an absent-or-empty field before any later rule can pass on it vacuously. Regression coverage: `tests/pipeline/test_anti_bluff_missing_evidence_fields.sh` CASES 1-3. Applies to `SKIPPED` records exactly as to `PASS`/`FAIL`. |
| `anti_bluff_status` | string | `"validated"` or `"REJECTED: <reason>"` — written by `anti-bluff-validate.sh` (R-009), not by the test itself. |

**Validation rules**: `result: PASS` with `anti_bluff_status` starting `"REJECTED"` MUST be treated as a failure for every downstream gate (FR-009) — the validator's verdict overrides the test's own self-reported result, by design (this is the entire mechanism FR-004 exists to provide).

**CORRECTED 2026-08-21 — this rule is now genuinely enforced end-to-end; for a period it was not.** See the Pipeline Run Report's own Validation rule at the bottom of this document for the full forensic note. In short: the counter this rule ultimately depends on (`evidence_summary.rejected_by_anti_bluff`) was seeded to `0` and never written by anything, so at the run level the override was a no-op. `recompute_evidence_summary` now derives it by scanning the real records on disk, and counts a `REJECTED` record **independently of its `result`** — a `REJECTED` record claiming `PASS` is the exact case the counter exists for. `phase-02-test.sh` applies the identical rule locally at the phase level.

**Two further rules the implementation added that this document did not originally state**, both fail-closed and both worth knowing before writing a record: a `result` value outside `PASS`/`FAIL`/`SKIPPED` is rejected outright rather than passing unexamined, and a `category` outside the schema's 8 enum values is likewise rejected — the Challenge-specific rule is selected by an exact string match on `real-device-challenge`, so an unrecognized category (a typo, a rename) would otherwise silently skip it. A `SKIPPED` record is validated through the EXACT SAME anti-bluff rules as `PASS`/`FAIL` records — a generic or missing `assertion_summary`/`raw_output_ref` gets a `SKIPPED` record `REJECTED` exactly like any other bluff attempt; `SKIPPED` is not an exemption from anti-bluff scrutiny, only from the false binary of PASS-or-FAIL. A validated `SKIPPED` record does NOT count toward `evidence_summary.rejected_by_anti_bluff` and does NOT by itself block a Pipeline Run's `outcome` from being `PASS` — a legitimately-skipped test, honestly reported, is not a failure of the pipeline; it is a documented, real absence of coverage for a documented reason.

## Submodule Advance Record

One record per submodule processed, written by **`scripts/advance-all-submodules.sh`** (per R-005).

> **CORRECTED 2026-08-21 — the writer named here does not exist.** The previous text said these records are written by `phase-07-closure.sh`. There is no `phase-07-closure.sh`: it is blocked behind T048/T049 (the Decoupled Reusable Architecture rule's "submodule fetch/pull is an EXPLICIT operator action, never automatic" carve-out) plus T054's mandatory review gate, and the orchestrator has no `closure` phase. The records are written by the standalone `scripts/advance-all-submodules.sh`, which **has never been run against a real submodule** — only against disposable git fixtures in `tests/pipeline/test_advance_all_submodules.sh`.
>
> **Path.** The default record directory is `.lava-ci-evidence/pipeline-runs/<run_id>/submodule-advances/` as documented, but it is derived from `LAVA_ADVANCE_RECORD_DIR`, falling back to `LAVA_PIPELINE_RUN_ID`. The script **refuses to run at all** (exit 2, nothing attempted) unless `LAVA_PIPELINE_RUN_ID` is set, or both `LAVA_ADVANCE_RECORD_DIR` and `LAVA_ADVANCE_VERIFY_CMD` are supplied — without a run id it cannot reach the R-005 step-5 rebuild-and-test, and it will not advance a pin it cannot honestly claim to have re-verified.
>
> **Filename.** `<submodule-name>.json` is imprecise: a submodule path contains `/`, which would make it a nested directory. The basename is the **sanitized** path (every character outside `[A-Za-z0-9._-]` becomes `_`), so `submodules/auth` writes `submodules_auth.json`. The `submodule_name` field inside the record keeps the real, slashed path.

## Pipeline Run Report

The single consolidated artifact (FR-019): `.lava-ci-evidence/pipeline-runs/<run_id>/report.json`.

| Field | Type | Notes |
|---|---|---|
| `run_id`, `commit_sha`, `started_at`, `completed_at`, `outcome` | — | Mirrors the Pipeline Run entity's own fields (this file IS that entity's persisted form). |
| `phases` | array | One entry per phase: `{name, result, duration_seconds, evidence_dir}` — matches the existing `.lava-ci-evidence/verify-all/<timestamp>.json`'s `{gates: [{name, result, duration_seconds}]}` shape (R-008). |
| `build_artifacts` | array of Build Artifact | |
| `evidence_summary` | object | `{total, passed, failed, skipped, rejected_by_anti_bluff}` counts — NOT the full Evidence Record contents (those stay in their own per-test files; this is the "read in one place" summary SC-008 requires). `skipped` counts validated Evidence Records whose `result` is `SKIPPED` (see the Evidence Record section above); it is tracked separately from `rejected_by_anti_bluff` because a legitimately-skipped, anti-bluff-validated test is not a rejection. |
| `distributions` | array of Distribution Record | **CORRECTED 2026-08-21: always empty today.** The field is seeded to `[]` and nothing appends to it — there is no distribute phase to reach (see the Distribution Record section above). Do not read an empty `distributions` as evidence that a run was blocked; it is empty on every run, passing or failing. |
| `submodule_advances` | array of Submodule Advance Record | **CORRECTED 2026-08-21: also always empty today.** Same reason — no closure phase is wired. `scripts/advance-all-submodules.sh` writes its records as **individual files** under `submodule-advances/`; nothing aggregates them back into this array, because the (unbuilt) closure phase was to be what did that. |

**Validation rule**: `outcome: PASS` MUST imply **`phases[]` is non-empty**, AND every phase entry's `result` is `PASS`, AND `evidence_summary.rejected_by_anti_bluff == 0` — this is the single field an operator or auditor checks first (SC-008), so it must never be true while an empty run, a phase, or an anti-bluff rejection says otherwise. `evidence_summary.skipped > 0` does NOT, by itself, prevent `outcome` from being `PASS` — a phase whose individual tests include one or more validated `SKIPPED` Evidence Records, with everything else `PASS`/validated, is still a genuine pass (see the Evidence Record section's `SKIPPED` design decision above).

**CORRECTED 2026-08-21 (a) — the non-empty clause was missing here and is load-bearing.** The rule as originally written was satisfied vacuously by a run with zero phases: nothing failed, nothing was rejected, so `outcome` would have been `PASS` for a run that proved nothing. `finalize_run_report` implements the rule with the non-empty guard included (`(.phases | length) > 0 and (.phases | all(.result == "PASS"))`), and `tests/pipeline/test_evidence_and_run_report.sh` Check 4c asserts the empty case yields `FAIL`. The same vacuous-pass shape was found and closed one level down, inside the test phase: `phase-02-test.sh` reported PASS when every dispatched wrapper exited 0 having written **zero Evidence Records between them** — no wrapper failed, no record said FAIL, no record was REJECTED, because there were no records. It now additionally requires at least one Evidence Record to have been scanned (regression coverage: `tests/pipeline/test_phase_02_aggregation.sh` CASE 2). The lesson generalizes to any rule of this shape: *"nothing bad was found"* is only a pass if something was actually looked at.

**CORRECTED 2026-08-21 (b) — the anti-bluff half of this rule was a no-op for real, and this is the defect this reconciliation most needed to record.** `finalize_run_report` implements the rule literally, reading `evidence_summary.rejected_by_anti_bluff`. But `init_run_report` seeds that counter to `0`, and **nothing ever wrote it**: `phase-02-test.sh` tallies the identical counters locally and prints them in its console summary, and never writes them back into `report.json`. So the condition that gates `PASS` on there being no anti-bluff rejection read a field that was permanently `0`, and a run whose Evidence Records had been `REJECTED` could still finalize to `PASS`. The rule looked enforced and was not — the exact bluff class this feature exists to evict, sitting in this feature's own report writer. Closed by `recompute_evidence_summary`, a fourth public function in `lib/run-report.sh` that rebuilds `evidence_summary` by **scanning the real Evidence Record files on disk** for the run, deliberately deriving every count from physical artifacts rather than from a counter each phase must remember to increment — a phase that forgets to report cannot thereby hide its own rejected evidence. It counts a record as rejected whenever `anti_bluff_status` begins with `REJECTED`, **independently of that record's own `result`**, and counts an unreadable record as failed rather than skipping it. The orchestrator calls it before `finalize_run_report` on **every** exit path, including an interrupt, and exits non-zero when every phase passed but the finalized `outcome` is not `PASS` — the finalized outcome is authoritative over the individual phase exit codes. Regression coverage: `tests/pipeline/test_run_report_evidence_summary.sh` CASE 3. `finalize_run_report` deliberately does **not** recompute the summary itself; supplying that input is a separate function's job, and the separation is itself asserted by `tests/pipeline/test_evidence_and_run_report.sh`.
