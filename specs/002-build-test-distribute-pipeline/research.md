## R-001: Constitutional amendment mechanism — how machine evidence substitutes for human attestation

**Decision**: Amend `CLAUDE.md` §6.AA and Seventh Law clause 3 to add an explicit alternate-path clause: when a distribution is produced by this pipeline (identified by the presence of a Pipeline Run Report for the exact commit SHA and versionCode being distributed, generated within the same run), the pipeline's own aggregated evidence — covering build success, 100% of FR-002's test categories passing with anti-bluff-validated evidence, and a live-verification pass against the actually-running services — satisfies the "real user has used the feature on a real device" requirement in place of a human doing so manually. The human-executed path (§6.AA two-stage + manual attestation) remains fully in force for any distribution NOT produced by this pipeline (e.g., an operator manually running `firebase-distribute.sh` outside the pipeline).

**Rationale**: This preserves the *safety property* the two clauses exist for (no distribution without real proof the feature works) while removing the specific *mechanism* (a human doing it) the operator explicitly chose to automate. Per the project's own Governance amendment procedure, the amendment must name what changed, why, and the migration plan — this alternate-path framing does that precisely, and is narrowly scoped (only this pipeline's own runs qualify) rather than broadly weakening the rule for all distributions.

**Alternatives considered**: (a) Deleting the human-attestation requirement outright — rejected, since it would also weaken the safety net for manual/ad-hoc distributions this pipeline doesn't cover. (b) Requiring the amendment to expire/require periodic re-ratification — rejected as unnecessary process overhead the spec didn't ask for.

**Implementation note (2026-08-21) — R-001's framing is INSUFFICIENT as scoped, and an amendment drafted on this analysis alone would authorize shipping the R8-minified release APK on debug-channel evidence.** R-001 reasons entirely at the level of *what the pipeline proves* and treats the distribution step as a neutral pipe. It is not neutral. Combine R-001 with R-003's decision to invoke `scripts/firebase-distribute.sh --debug-and-release` and three facts in that script — each read directly, not inferred — compose into a gap R-001 does not close:

1. `--debug-and-release` (and its alias `--both`) sets `MODE="both"`.
2. The script's **§6.AA staging gate is guarded on `MODE == "release"`**. With `MODE=both` that branch never evaluates, so the check that debug stage 1 already distributed this versionCode simply does not run. This is not incidental: the gate's own failure message offers, as remedy (b), *"operator-pre-authorize combined distribute via `--debug-and-release` (NOT recommended; bypasses staging)"* — the script names `--both` as the staging bypass.
3. The **§6.AK cycle-coverage gate resolves its evidence channel from the same variable**: `case "$MODE" in release) AK_CHANNEL="release" ;; *) AK_CHANNEL="debug" ;; esac`. `MODE=both` falls to the default arm and is gated against the **debug** channel's §6.Z evidence — while, later in the same run, the **release** APK is uploaded.

Net effect: under `--debug-and-release` the release artifact ships having been gated against debug-channel evidence, with the two-stage check never evaluated. That is materially weaker than what a bare `--release-only` invocation must satisfy, and it is the precise shape of the 1.2.19-1039 forensic anchor that birthed §6.AA in the first place — an R8-minified release build whose failure mode did not exist in the debug variant. R-001's "the pipeline's own aggregated evidence substitutes for the human check" is a claim about evidence *sufficiency*; it never asks **which artifact the evidence actually covers**. An amendment scoped on R-001 alone would therefore hand the pipeline an authorization broader than its evidence supports.

What this does **not** say: it does not say `MODE=both` is broken, and it does not contradict R-003's narrow finding that no code change is needed for the script to *run* in combined mode (see R-003's own note below). It says the constitutional amendment R-001 proposes must be scoped in terms of the **artifact and channel the evidence covers**, not merely "this pipeline produced it". Any amendment text that lands for tasks T040/T041 needs to address this explicitly — for example by requiring the pipeline to invoke the two stages separately so both gates evaluate as designed, or by requiring the release-channel evidence to exist in its own right before a combined invocation is permitted. Recorded here as an open design question, not as a resolved decision. The amendments remain unapproved as of this date, `phase-05-distribute.sh` does not exist, and the orchestrator cannot distribute anything by construction — so nothing has shipped through this gap.

## R-003: `firebase-distribute.sh` already supports unattended combined distribution — no script change needed

**Decision**: `phase-05-distribute.sh` invokes the existing `scripts/firebase-distribute.sh --debug-and-release --app client` and `--app api-app`, per app. No modification to `firebase-distribute.sh` itself is required.

**Rationale**: Reading the script directly: `--debug-and-release`/`--both` already exists as `MODE=both`, and none of its runtime gates (`§6.P` version-monotonic check, `§6.AA` release-requires-prior-debug check, CHANGELOG-entry check, snapshot-file check, pepper-rotation check) special-case or block `MODE=both` beyond what `MODE=debug`/`MODE=release` already independently require. The header comment's "(NOT recommended; bypasses staging)" is prose guidance for a human operator, not an enforced code gate — there is no interactive prompt, no confirmation flag, no environment-variable authorization check anywhere in the script for `MODE=both`. The constitutional change this feature needs is entirely in `CLAUDE.md`'s text (R-001) and in this pipeline's own decision to invoke `--both`, not in the distribution script's mechanics.

**Alternatives considered**: Forking `firebase-distribute.sh` or adding a new `--pipeline-authorized` flag — rejected as unnecessary; the existing `--both` flag already does exactly what's needed, and duplicating the script would violate this project's own "no parallel implementation" Local-Only CI/CD principle (the same script a human could run must be what the pipeline runs).

**Implementation note (2026-08-21) — the narrow finding holds; the framing points the wrong way.** Re-read against the current script, R-003's literal claims are accurate: `--debug-and-release`/`--both` does exist and does set `MODE=both`; there is no interactive prompt, no confirmation flag, and no environment-variable authorization check for it; and the header's "(NOT recommended; bypasses staging)" is indeed prose, not an enforced code gate. No change to `firebase-distribute.sh` is needed for the pipeline to invoke it.

But the sentence *"none of its runtime gates ... special-case or block `MODE=both` beyond what `MODE=debug`/`MODE=release` already independently require"* asks only whether combined mode is **blocked**, and the real risk is the reverse: `MODE=both` is **less gated** than `MODE=release`. The §6.AA staging gate is guarded on `MODE == "release"` and never evaluates in combined mode, and the §6.AK cycle-coverage gate resolves to the **debug** channel for any mode that is not exactly `release` — while the release APK is uploaded regardless. See the full R-001 note above; the two findings are one finding, and it belongs to the amendment's scope (R-001), not to this script's mechanics (R-003). The rejection of a fork or a `--pipeline-authorized` flag still stands on its own merits.
## R-004: Gate ordering — CHANGELOG entry and version snapshot must exist *before* invoking `firebase-distribute.sh`

**Decision**: Split the "documentation" work into two ordered sub-steps: `phase-05a-changelog-entry.sh` (writes the `CHANGELOG.md` entry + `.lava-ci-evidence/distribute-changelog/<channel>/<version>-<code>.md` snapshot for the exact version about to be built) runs *before* `phase-05-distribute.sh`; the broader `phase-06-docs.sh` (FAQs, diagrams/schemes, `docs/ARCHITECTURE.md` staleness fixes per R-002) runs *after* distribution succeeds.

The spec's User Story 3 groups "distribute" and "refresh documentation" together, but the actual dependency direction for the CHANGELOG specifically is inverted from a naive reading: distribution needs the CHANGELOG entry to already exist, not the reverse.

**Alternatives considered**: Having `firebase-distribute.sh` author its own CHANGELOG entry — rejected; that script's existing contract treats the CHANGELOG as an input it verifies, and changing that contract is out of scope for this feature and would touch a widely-depended-on gate script beyond what's needed.

## R-005: Submodule pin-advance mechanics (FR-015)

**Decision**: `scripts/advance-all-submodules.sh` operates per-submodule in this order: (1) `git -C submodules/<name> fetch --all`; (2) compare current pinned commit to the remote's default-branch HEAD; (3) if identical, no-op (per spec Edge Case); (4) if different, checkout the remote HEAD into the submodule's working tree; (5) rebuild + re-run the affected test categories from `phase-01-build.sh`/`phase-02-test.sh` against the advanced state — if this fails, discard the advance for that submodule (checkout back to the prior pin) and report the specific incompatibility, per the spec's breaking-change edge case, rather than committing a pin bump that broke the build; (6) if the submodule itself has local, uncommitted modifications (independent of the advance), commit and push those to its own upstream(s) per the existing §6.W two-mirror scope; (7) `git add submodules/<name>` in the parent repository to record the new pin.

**Rationale**: This ordering makes the "advance breaks the build" edge case mechanically enforceable (rebuild-and-test-before-committing-the-pin) rather than a documentation-only promise, and keeps the submodule's own commit/push step (which the submodule's own upstream, not this repo, is authoritative for) cleanly separated from the parent's pin-update step.

**Alternatives considered**: Advancing all submodule pins first and only then running the full test suite once at the end — rejected because a single failure would be ambiguous about which submodule's advance caused it, and would leave the parent repository's pins reflecting a broken combination.

**Implementation note (2026-08-21) — implemented as specified, plus three properties R-005 did not name.** `scripts/advance-all-submodules.sh` follows the 7-step ordering above verbatim. Three things the implementation added that this decision did not anticipate, each worth carrying forward into any future design of this kind:

1. **Step 5 is a hard precondition, not a step that can be skipped.** The script **refuses to run at all** (exit 2, nothing attempted) unless it can reach a real rebuild-and-test: `LAVA_PIPELINE_RUN_ID` must be set, or both `LAVA_ADVANCE_RECORD_DIR` and `LAVA_ADVANCE_VERIFY_CMD` must be supplied. R-005 described step 5 as part of the sequence; making it a refusal condition means the script cannot advance a pin it is unable to honestly claim to have re-verified.
2. **Step 7 stages only.** `git add <submodule-path>` is where it stops — it **never commits in the parent repository**, so a human review gate sits between "pins staged" and "pins pushed". A run therefore leaves the parent tree with staged changes, not clean; `quickstart.md` Scenario 4 asserted the opposite and has been corrected.
3. **Discarding an advance never destroys local work.** When step 6 had to commit local submodule modifications before a push that then failed, that commit is preserved under `refs/lava-advance-rescue/<id>` in the submodule before HEAD is moved back to the prior pin, so the work stays reachable rather than reflog-only.

**Status**: the TDD cycle is complete against disposable git fixtures (`tests/pipeline/test_advance_all_submodules.sh`). It has **never been run against a real submodule upstream** — `plan.md`'s Human Checkpoint #2 (task T054) is not cleared, and the amendment this whole step depends on (T048/T049) is unapproved.

## R-012: Reuse the existing systemd --user wiring wholesale (correction to R-006/R-007)

**Decision**: `phase-03-install-boot.sh` does NOT create a new unit template or new install logic. It is thin glue over three scripts that already exist, are already committed, and were already installed-and-verified for real (per commit `7951bf4f`'s own commit body, which records a genuine `journalctl`-confirmed version match, not an assumed success):

1. `scripts/systemd-uninstall.sh` (FR-007's stale-instance cleanup, if a prior unit is active)
2. `scripts/systemd-install.sh --start` (installs `systemd/user/lava-api.service.template` — note the existing filename is `lava-api.service.template`, not `lava-api-go.service.template` as R-006 assumed — to `~/.config/systemd/user/lava-api.service`, `daemon-reload`, `enable`, `loginctl enable-linger`, and starts it)
3. `scripts/systemd-status.sh` (FR-006's health check — already reports BOTH `systemctl --user status` AND the real container-level health via `tools/lava-containers/bin/lava-containers -cmd=status`, already designed with §6.B "unit-active is not application-healthy" awareness)

`phase-03-install-boot.sh`'s only new code is: (a) parsing `systemd-status.sh`'s output (or, more robustly, calling `tools/lava-containers/bin/lava-containers -cmd=status` directly and checking its own `Healthy:` field, since that binary's output is more machine-parseable than the human-readable wrapper) into a proper Infrastructure Service record per `data-model.md`, and (b) the FR-007 stale-check logic (query `systemctl --user is-active lava-api.service` before deciding whether to uninstall-then-reinstall vs. install-fresh).

The existing unit already wraps `start.sh`/`stop.sh` (the containerized podman path), not a bare `lava-api-go` binary process directly — this is consistent with, not a contradiction of, R-002's artifact-set finding: `lava-api-go`'s binary (built in T019 / `phase-01-build.sh`) is what gets packaged INTO the container image `start.sh` builds and runs; the systemd unit manages the container's lifecycle, matching this project's actual current deployment model.

**Rationale**: Building a new systemd template and install script when a real, tested, already-verified one exists would violate the same Local-Only CI/CD "no parallel implementation" principle this plan's Constitution Check already relies on for R-003 (`firebase-distribute.sh` reuse) — the standard this plan holds itself to for one script must apply equally here. It would also silently produce TWO systemd units for the same service (`lava-api.service` from the existing commit, plus a hypothetical new `lava-api-go.service` from R-006's original draft) — a real operational hazard, not just a style concern.

**Alternatives considered**: Extending `systemd-status.sh` itself to emit JSON — rejected for now as unnecessary scope growth; calling the underlying `lava-containers -cmd=status` binary directly from `phase-03-install-boot.sh` gets the same machine-readable signal without modifying an existing, working script.

**Implementation note (2026-08-21) — R-012 is accurate and shipped, with one substitution.** `phase-03-install-boot.sh` invokes `scripts/systemd-uninstall.sh` and `scripts/systemd-install.sh --start` verbatim and reimplements none of their unit-rendering, `daemon-reload`, `enable` or linger logic. It does **not** invoke the third script, `scripts/systemd-status.sh`, at all: it takes the option R-012's own "Alternatives considered" paragraph flagged as the more robust one and calls `tools/lava-containers/bin/lava-containers -cmd=status` directly for a machine-parseable signal. That choice turned out to matter more than "more parseable": the binary's `Manager.Status()` returns nil regardless of the probed health value, so it **exits 0 even when the service is unhealthy**. Trusting its exit code would have been precisely the §6.B "container Up is not application-healthy" bluff, so the load-bearing signal is the printed `Healthy:` field, matched case-insensitively, with an unparseable output treated as a failure rather than an unknown. The one Infrastructure Service record R-012 clause (a) called for is written instead as a normal Evidence Record, which puts it through the same anti-bluff validator as everything else — see `data-model.md`'s Infrastructure Service section.

**Process note**: This correction was only caught because Setup-phase work (creating `systemd/user/`) surfaced the existing template file already present in that directory. The Phase 0 research pass (R-001 through R-011) did not independently verify systemd/user/ was empty before designing R-006/R-007 from scratch — an honest gap in the planning discipline that R-002/R-003 (which WERE verified against the live repo) did not have. Recorded here so a future feature's planning phase treats "check for existing prior art in the exact directory this feature is about to populate" as a standing step, not just "check the artifact/module list."

## R-008: Evidence Record and Pipeline Run Report format

**Decision**: Every Evidence Record is a single JSON file, one per executed test, at `.lava-ci-evidence/pipeline-runs/<UTC-timestamp>/phase-<NN>/<test-category>/<test-id>.json`, with a fixed minimal schema (`test_id`, `category`, `command`, `result` [`PASS`|`FAIL`], `assertion_summary`, `raw_output_ref`, `anti_bluff_status`). The Pipeline Run Report (`report.json` at the run directory's root) aggregates these by reference (path, not duplicated content) plus per-phase pass/fail/duration, Distribution Records, and Submodule Advance Records.

**Rationale**: Matches this project's existing, already-established evidence conventions (`.lava-ci-evidence/verify-all/<timestamp>.json`'s `{gates: [{name, result, ...}]}` shape, `.lava-ci-evidence/bluff-hunt/<date>.json`) rather than inventing a new format — consistency here means existing tooling (and future audits) can reason about pipeline evidence the same way they already reason about every other gate's evidence.

**Alternatives considered**: One giant report file with all raw output inline — rejected; would make individual test evidence hard to independently re-verify (FR-003's explicit requirement) and would bloat the aggregator file needed for FR-019/SC-008's "read in one place" goal.

**Implementation note (2026-08-21) — the format landed as designed, with one enum widened and one aggregation function that this decision did not foresee needing.** `result` shipped as **`PASS` | `FAIL` | `SKIPPED`**, not the two-value `[PASS|FAIL]` recorded above: an honestly-skipped test (a Go test's own `t.Skip(...)`, or a check blocked by a genuinely missing host precondition) has no truthful home in a two-value enum — forcing it to `FAIL` misreports a non-defect, and forcing it to `PASS` fabricates a result for something that never ran. A `SKIPPED` record goes through the identical anti-bluff rules and is not exempt from any of them.

The aggregate-by-reference design also turned out to need an explicit **recomputation** step that nothing in R-008 called for. `report.json`'s `evidence_summary` is not written by the phases that produce the records; it is rebuilt by scanning the real record files on disk at the end of the run. Until that function existed the summary stayed at its seeded zeros, which silently disabled the run-level anti-bluff rule that reads it — see `data-model.md`'s Pipeline Run Report Validation rule for the full forensic note. The generalizable lesson for an aggregate-by-reference format: **derive the aggregate from the referenced artifacts, never from a counter each producer must remember to increment**, or a producer that forgets to report can hide its own bad news.
## R-009: Anti-bluff evidence validator design (FR-004)

**Decision**: `scripts/pipeline/lib/anti-bluff-validate.sh` is a rule-based validator checking each Evidence Record against the Seventh Law clause 4 Forbidden Test Patterns list mechanically where possible: (a) reject a record whose `assertion_summary` matches only generic strings ("did not crash", "process completed", "BUILD SUCCESSFUL" with no other content); (b) reject a Challenge-category record lacking a falsifiability-rehearsal reference (reusing `scripts/check-challenge-discrimination.sh`'s existing detection logic rather than re-implementing it); (c) reject any record whose `raw_output_ref` file does not exist or is empty (an evidence record must point at real captured output). Records that pass all checks are marked `anti_bluff_status: "validated"`; anything failing is marked `"REJECTED: <reason>"` and the corresponding test is treated as failed for FR-009's purposes regardless of its own `result` field.

**Rationale**: This directly operationalizes clause 4's existing forbidden-pattern list mechanically rather than trusting each test category's own reporting to be honest — the whole point of FR-004. Reusing `check-challenge-discrimination.sh` for the Challenge-specific check avoids re-deriving logic that already exists and is already tested.

**Alternatives considered**: Trusting each phase's own `PASS`/`FAIL` exit code without a separate validation pass — rejected; this is precisely the "CI green is necessary, not sufficient" failure mode Sixth Law clause 5 and this feature's own FR-004 exist to prevent.

**Implementation note (2026-08-21) — the design is sound and shipped; all three named rules needed correcting in contact with reality.** Taking them in order:

**Rule (a), generic-string rejection — the matching strategy was falsified by a real run.** The rule as designed rejects a summary "matching only generic strings". The first implementation substring-matched `"did not crash"`, `"process completed"` and `"no crash"` **anywhere** in the summary, on the theory that those phrases describe nothing but absence-of-detail no matter what surrounds them. A real run of this project's actual Kotlin suite falsified that: it rejected **5 genuine PASS records**, because the Kotlin wrapper's PASS template quotes the real test's own name verbatim and several test authors legitimately named tests with "no crash" as **specific** content (one real example describes emitting an empty list when a key holder is locked, "no crash on search path" — a real description of what is verified, not a lazy summary). Corrected to apply the same "nothing else specific left" standard the `"build successful"` phrase already used: reject only when removing every occurrence of the phrase leaves negligible content behind. `"build successful"` remains an exact match, since a genuinely specific summary may legitimately quote it as one verbatim fact among several.

**Rule (b), the Challenge falsifiability marker — could not literally reuse the existing detector.** R-009 says to reuse `scripts/check-challenge-discrimination.sh`'s detection logic "rather than re-implementing it". Its marker regex is mirrored, but its "or a companion JSON file carrying a `falsifiability_rehearsal`/`discrimination` field" branch **cannot** be reused as written: `contracts/evidence-record.schema.json` sets `"additionalProperties": false`, so there is no room for a `falsifiability_ref` property without breaking schema validation. The validator instead searches the two real-text surfaces the schema already provides — the record's own `assertion_summary`, and the full contents of the file its `raw_output_ref` points at (which by that point the preceding rules have proven is a real, non-empty file). `raw_output_ref` **is** the companion evidence, reusing a field the schema defines rather than inventing one it forbids.

**Rule (c), "does not exist or is empty" — unenforceable exactly as written, and this is the important one.** Both halves of that test are satisfied by a **directory**: an absent or empty `raw_output_ref` resolved to `"<record_dir>/"`, the record's own directory, which exists and whose inode has a non-zero size. So the two rules whose entire job is "there is real captured output behind this claim" both passed on nothing at all, and a record that asserted nothing and pointed at nothing was stamped `"validated"`. Two changes close it: the resolved path must now be a **regular file** (`-f`, not `-e`), and a separate earlier check rejects any schema-required field that is absent or empty — necessary because `jq -r '.x // empty'` cannot distinguish an absent field from an empty one, so absence never reached the later tests and satisfied every one of them vacuously. Regression coverage: `tests/pipeline/test_anti_bluff_missing_evidence_fields.sh` CASES 1-3.

**Two fail-closed rules were added that R-009 did not specify**, both closing the same shape of gap: a `result` outside the schema's enum is rejected outright (the validator originally never inspected `result`'s value at all), and a `category` outside the schema's 8 enum values is rejected (rule (b) is selected by an exact match on `real-device-challenge`, so an unrecognized category — a typo, a rename — would silently skip it).

The generalizable finding across all three: **every one of these was a rule that could not fail on the input it existed to catch.** A validator's own rules need the same falsifiability standard it applies to the tests it validates.
## R-010: "Always restart from scratch" mechanics (FR-018)

**Decision**: Each pipeline invocation creates a fresh `.lava-ci-evidence/pipeline-runs/<UTC-timestamp-of-this-run>/` directory and never reads from any other timestamped run directory as live input (existing directories are historical record only, exactly like every other `.lava-ci-evidence/<timestamp>/` convention already in this project). `phase-03-install-boot.sh` additionally checks for and stops any `lava-api-go` systemd user unit already active under the current user session (regardless of which run started it) before starting a fresh instance, satisfying FR-007 without needing to persist any run-to-run state file.

**Rationale**: Timestamped, non-overwriting directories are how every other gate in this project already records evidence — reusing that convention means "restart from scratch" requires no new state-tracking mechanism at all; the filesystem's own directory listing is the implicit history.

**Alternatives considered**: A single mutable `current-run/` symlink or state file — rejected; adds a stateful component this feature's own Clarification (no resume, ever) makes unnecessary, and risks exactly the kind of "an old symlink didn't update" bug class this project's forensic history already contains several examples of (e.g., the stale-CamelCase-submodule-list bug in an earlier constitution-checker cycle).

**Implementation note (2026-08-21) — implemented as designed; two details to record.** The stale-service check names the unit **`lava-api.service`**; this entry still says `lava-api-go` systemd user unit, carrying forward R-006's original wrong name that R-012 corrected. And the check is `systemctl --user is-active lava-api.service`, treating the literal answer `active` as stale — **no timestamp comparison of any kind**, which is what makes R-010's "without needing to persist any run-to-run state file" claim actually true, and which also catches an instance started by a manual `./start.sh` or by the unit's own enable+linger across a reboot, neither of which a run-scoped comparison would have caught.

The no-reuse property gained one mechanical guard the design did not call for: `init_run_report` **refuses** when a `report.json` already exists for the given `run_id`, so an accidental collision cannot silently destroy an earlier run's evidence. Because `run_id` has one-second resolution, two invocations started inside the same second do collide, and the second is refused rather than allowed to overwrite.

**Implementation note (2026-08-21) — the mapping is accurate; three things about it are not what this table implies.**

1. **`scripts/ci.sh` is never invoked by this pipeline.** The last sentence above treats it as the test-orchestration surface, and `plan.md` listed it as one of the existing scripts the orchestrator is thin glue over. Neither is true in the implementation, deliberately: the constitutional-gate-sweep wrapper calls `scripts/verify-all-constitution-rules.sh --json-only` **directly**, because `ci.sh` invokes Gradle heavily and the sweep is the one step inside it this category actually needs; and the hermetic wrapper enumerates and runs the `tests/*/` suites itself. Both scripts say so explicitly in their own headers. `ci.sh` remains this project's pre-push/pre-tag surface and is unchanged — it is simply not on this pipeline's call path.
2. **The 8 categories are covered by 7 wrapper scripts, not 8.** One wrapper covers both `go-unit-integration` and `real-binary-contract`, since both are `go test` invocations over the same module.
3. **"Evidence-record wrapper only" understated the work considerably.** Each wrapper had to parse a real tool's real output format honestly — Gradle's JUnit XML, `go test`'s output, the chaos harness's evidence JSON, the sweep's attestation JSON — and each is several hundred lines, most of it about **not** reporting a pass it cannot back. Real defects were found in that process, including one where `jq`'s `//` operator falls back on boolean `false` as well as null, so a sweep attestation genuinely reporting `"all_passed": false` was recorded in every Evidence Record as `"unknown"`.

**On "test types newly created by this feature: none identified"** — that resolution held at the level it was asked: no new test *category* was needed, and every category already had real tooling. But the feature did create a substantial new body of tests — the hermetic suites under `tests/pipeline/`, several of them written specifically to lock down defects found while building the wrappers and the report writer. Those are new tests, not a new category, and they are where this feature's own falsifiability lives.
